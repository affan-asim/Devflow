## 3. Concise 5-Minute Presentation Explanation

**The DevFlow platform is a full-stack recruitment management system built on Next.js 16 with App Router, using PostgreSQL via Prisma ORM, Redis for caching/rate-limiting, and BullMQ for background job processing.**

### Request Lifecycle:
1. **Browser** sends HTTP with JWT access-token cookie
2. **proxy.js** verifies JWT, checks Redis token-bucket rate limit (Lua script), attaches `x-user-id`/`x-user-role` headers
3. **Route handler** validates Zod schema, calls service layer
4. **Service** performs Prisma DB operations, may add BullMQ jobs (email/notification/storage)
5. **Background workers** process jobs: Email via Resend, Storage via S3 presigned URLs
6. **Dashboard** reads cached metrics from Redis (5-min TTL) or queries Prisma directly
7. **Rate limiter** per-user in Redis with token bucket (Lua script), same as proxy's one.

### Key Data Flows:
- **User onboarding**: Register → OTP via Redis (fallback to Postgres) → Email queue → Resend API → Verification
- **Company verification**: Admin PATCH → Prisma update → Notification queue → Resend email → Recruiter notified
- **Job application**: Create application → Prisma transaction → Dashboard metrics updated (cache invalidated)

### 7 Service Areas Monitored:
PostgreSQL, Redis, S3 storage, 3 BullMQ queues (email, notification, storage), plus overall system health status.

## 4. Three Architecture Decisions & Trade-offs

### Decision 1: Proxy.js over Deprecated Middleware
- **What**: Using Next.js `proxy.js` (app router style) instead of deprecated `middleware.js`
- **Trade-off**: Proxy can modify responses and run before route rendering, but cannot depend on shared modules/globals per documentation notes. The codebase has comments acknowledging this limitation.

### Decision 2: Redis Primary with PostgreSQL Fallback
- **What**: Redis for rate limiting, OTP storage, dashboard metrics with Postgres fallback
- **Trade-off**: Ensures continuity when Redis is down (seen in `authService.js` fallback to `verificationOtp` table), but rate limiting bypasses entirely on Redis errors ( `proxy.js` lines 92-94), potentially allowing request floods.

### Decision 3: BullMQ Workers + Lua Token Bucket Rate Limiting
- **What**: Email workers limited to 5 concurrency with 2 jobs/1s limiter on queue level beacuse as resend api request should not be more than 2 req/second; API rate limiting via Redis token bucket (10 tokens, 1/sec refill)
- **Trade-off**: Concurrency limits improve stability but increase delivery latency. Token bucket provides smooth throttling but may reject request bursts even when total capacity exists across multiple users.

## 5. Two Evidence-Based Reliability/Security Gaps

### Gap 1: Redis Failure Bypasses Rate Limiting
- **Evidence**: `proxy.js` lines 88, 98 — if `tokenBucket()` Redis call throws, the error is caught and the request bypasses rate limiting entirely (`if (!res) { return 429 }` is skipped).
- **Impact**: Potential request flooding when Redis is unavailable.

### Gap 2: Cookie-Based Auth Without Explicit CSRF Validation
- **Evidence**: Login sets `httpOnly` cookies with `sameSite: "lax"`, and `axios` instance uses `withCredentials: true`. However, no CSRF tokens are validated for state-changing operations. The `proxy.js` uses `accessToken` from cookies but doesn't enforce CSRF double-submit pattern.
- **Impact**: Potential CSRF vulnerability for state-changing requests if user visits malicious site while authenticated. -->


  A. Audit Summary

  The original diagram's layering is broadly correct, but it contains five factual errors, two missing subsystems, and several arrows that do  not match the code. The most important corrections:

  1. "Next.js Proxy / Middleware" is actually src/proxy.js — a Next.js 16 Proxy, not middleware. It verifies JWTs, rotates refresh tokens,   
     runs Redis rate limiting, and injects x-user-id/x-user-role from the verified token only. It does not do role routing or authorization. 
  2. Authorization is per-route, not in the proxy. Every protected handler re-checks roles against req.headers (e.g. jobs/[id]/route.js:42,  
     admin/dashboard/route.js:11). The proxy is an authentication + rate-limit boundary; authorization is defense-in-depth at the service    
     edge.
  3. Storage is Supabase Storage, not "Object Storage" and not AWS S3. src/services/presignedUrl/presignedUrl.js, the storage worker, and the     client uploader (src/lib/storage/uploadFile.js → supabase.storage) all use Supabase. The AWS S3 SDK is installed and src/utils/s3.js    
     exports a lazy S3Client, but no active code path calls it — it is dead code.
  4. Email is Resend (src/utils/resend.js).
  5. BullMQ shares the same Redis instance as cache, OTP, and rate limiting — all four queues use connectionOptions from src/lib/redis.js.   
     The diagram's separate "Redis" and "BullMQ" boxes should be one node.
  6. Zod validation runs after authentication, inside each route handler, before the service call.
  7. Missing subsystem: Admin monitoring & observability — dashboard metrics (Redis-cached), queue ops/failed-job retry, system-health checks     (DB/Redis/queues/Supabase), email-log auditing, and multi-domain analytics (users/jobs/applications/companies). All implemented, not    
     speculative.
  8. Worker→database edges exist and should be drawn: Email worker writes EmailLog; Notification worker writes Notification; Storage worker  
     updates File/Application/DeveloperProfile/RecruiterProfile in a Prisma transaction and deletes from Supabase; Job-expiration worker     
     updates Job.status.

  E. Presentation Notes (~5 minutes)

  "DevFlow is a Next.js 16 monolith with a clean four-tier synchronous path and a separate asynchronous worker plane.

  Request flow. A browser talks Redux Toolkit + Axios to the Next.js Proxy (src/proxy.js). The proxy is your single request-interception     
  point: it verifies the JWT access token with jose, transparently rotates it via the refresh endpoint when expired, runs a Redis
  token-bucket rate limiter, and then injects x-user-id and x-user-role headers — but only from the verified token. Any client-supplied      
  identity headers are stripped first on public routes. This is the right pattern: the proxy establishes who the caller is, but it does not  
  decide what they may do.

  Authorization is enforced at the route, not the proxy. Every protected handler re-reads those headers and checks roles itself — PATCH      
  /api/jobs/[id] requires RECRUITER, the admin dashboard requires ADMIN, and file access goes through multi-hop ownership checks in
  getFileUrl that trace applications, companies, and recruiter history. So the proxy is an authentication boundary; authorization is
  defense-in-depth at the service edge.

  Validation sits between auth and logic. Each handler parses the body with a Zod schema after reading the identity headers and before       
  calling the service. Services then do the real ownership and state checks against Prisma/PostgreSQL.

  The async plane. Services enqueue BullMQ jobs into Redis — the same Redis used for caching, OTP, and rate limiting. Four workers consume:  
  the Email worker sends via Resend and records an EmailLog; the Notification worker writes a Notification row; the Storage worker promotes  
  temp files in Supabase Storage and updates the File/Application/Profile tables atomically in a Prisma transaction; and a daily-cron Job    
  Expiration worker flips expired jobs to EXPIRED. Retries are configured declaratively (3 attempts, exponential backoff), but there is no   
  dead-letter queue — failure alerting is only a console comment.

  Admin monitoring is a real subsystem, not afterthought code. There are dashboard metrics cached in Redis, queue inspection with manual     
  failed-job retry, a system-health endpoint that pings PostgreSQL, Redis, all three queues, and Supabase storage, plus an email-log audit   
  trail and multi-domain analytics.

  Three engineering trade-offs worth discussing.

  1. Shared Redis for cache and queues. One Redis instance serves read-cache, OTP store, rate limiter, and BullMQ. This is simple and cheap, 
     but a cache stampede or a slow worker can starve the rate limiter, and a Redis outage silently disables both caching and queue
     processing — note the proxy bypasses the rate limiter on Redis error rather than failing closed.
  2. Trust-the-header authorization. Routes authorize off proxy-injected headers. This is fast and stateless, but it means the proxy is a    
     single point of trust: if it is bypassed (misconfiguration, direct invocation), headers are spoofable. The mitigating factor is that    
     getCurrentUser() in server utilities independently re-verifies the access token against the database, so the safest server-side reads go     through that path, not the headers.
  3. Supabase Storage with an unused AWS S3 SDK. The live storage path is Supabase, but the AWS S3 SDK is installed and a lazy S3 client     
     exists in src/utils/s3.js that nothing calls. That is dead weight and a migration landmine — a presenter should either remove it or     
     explicitly note that storage is Supabase, not S3."

  F. Security Observations

  Confirmed (evidence-backed):

  1. Identity headers are proxy-derived, not client-trusted. src/proxy.js:123-131 explicitly deletes x-user-id/x-user-role on public APIs and     re-sets them only from the decoded JWT. For non-public routes, proxy.js:144-146 sets them from the decoded token. A client cannot spoof 
     identity through these headers in normal flow. ✅
  2. Unauthenticated API requests are rejected. src/proxy.js:138-140 returns 401 for unauthenticated /api/* calls; unauthenticated page      
     requests redirect to /login. ✅
  3. Refresh tokens are hashed at rest and rotated. src/services/auth/refreshService.js stores SHA-256 hashes, revokes the old token on      
     refresh, and rejects revoked/expired sessions. ✅
  4. Rate limiting is Redis-backed with a Lua token bucket, keyed by userId for authenticated callers and by IP for anonymous. ✅
  5. Weak JWT secret fallback. src/proxy.js:24 uses process.env.SECRET_KEY || 'your-secret-key'. If SECRET_KEY is unset in production, tokens     are signed with a public string. Recommended test: assert the proxy rejects tokens signed with the literal 'your-secret-key' when       
     SECRET_KEY is set, and that deployment configs always set SECRET_KEY.
  6. Hardcoded email recipient. Every sendEmail in src/services/auth/emailNotifications.js sends to ['affanasim900@gmail.com'] regardless of 
     the actual recipient argument. In production this means user-facing emails go to a fixed address. Recommended test: send a registration 
     request and confirm the OTP email reaches the registering address.
  7. Rate limiter fails open. src/proxy.js:92-94,102-104,111-113 catches Redis errors and continues without limiting. Intended as
     availability trade-off, but it means Redis exhaustion → no throttling. Recommended test: simulate Redis ERROR from the Lua script and   
     confirm unlimited requests pass.
  8. No CSRF protection visible. State-changing endpoints (login, register, job create/update) read req.json() with no CSRF token check.     
     Cookie-based auth + sameSite: lax provides partial browser protection. Recommended test: attempt a cross-site POST from a form on       
     another origin and confirm behavior.
  9. Authorization depends entirely on the proxy. If the matcher is misconfigured or the proxy is disabled, x-user-id/x-user-role are absent 
     and handlers either 403 (admin/dashboard) or proceed without a role check (e.g., PATCH /api/jobs/[id] checks role but GET /api/jobs/[id]     does not). Recommended test: call GET /api/jobs/[id] with a spoofed x-user-id header pointing at another user's job and confirm the     
     service enforces ownership (getJob filters recruiters by profile.companyId at jobService.js:490-492).

  Requiring further testing (not confirmed from source):

  - Whether the storage worker's prisma.file.deleteMany on failure is safe (it is wrapped in .catch, so a failed Supabase delete still       
    removes the DB row — a potential orphaned-record race).
  - Whether the email worker's emailLog.upsert with id: job.data.emailLogId || String(job.id) can collide across workers.
  - End-to-end job-expiration: confirm expirePastDeadlineJobs sets EXPIRED and that expired jobs are not served publicly.
  - Whether deleteJobByAdmin skipping the applicant check (jobService.js:764-787) is intentional.
