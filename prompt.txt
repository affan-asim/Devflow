At a high level, DevFlow is organized into several layers, each with a different responsibility.
Starting from the client side, the application uses the Next.js App Router for the interface, with Redux Toolkit for client-side state management and Axios for HTTP requests. The interface covers the public marketplace as well as the developer, recruiter, and admin experiences.
When a request reaches the server, it passes through the Next.js Proxy. In my implementation, the proxy is responsible for JWT verification, refresh-token handling, Redis-backed rate limiting, and forwarding identity information derived from the verified token.
One important distinction is that the proxy does not replace authorization checks in the backend. The API route handlers apply the relevant role checks, and the input is validated where required. The service layer then handles the actual business operations, including the applicable ownership and business-rule checks.
For data persistence, I'm using Prisma with PostgreSQL. PostgreSQL stores the main relational data, such as users, companies, jobs, applications, and their associated records. Prisma provides the data-access layer that the application uses to interact with that database.
Redis has several responsibilities in this system. It's used for caching, OTP-related operations, and rate limiting. It also supports BullMQ, which I use to process certain tasks asynchronously.
The background workers run separately from the request-handling path. For example, the email worker sends messages through Resend and records email logs. The notification worker handles notification records, the storage worker processes storage-related tasks using Supabase Storage, and the job-expiration worker runs a scheduled task to update expired jobs.
This separation allows the application to handle work outside the immediate HTTP request where appropriate. It also introduces additional responsibilities, such as monitoring queues, handling failed jobs, and understanding what happens when Redis or a worker becomes unavailable.
The diagram also includes the administrative operations. Beyond the regular user-facing features, the admin area provides analytics, dashboard metrics, system-health information, email-log visibility, and queue operations such as inspecting or retrying failed jobs.
There's also a direct upload path to Supabase Storage using a signed URL, where implemented. This lets the browser transfer file data directly to the storage service rather than sending the entire file through the application server.
One important trade-off in this architecture is that Redis supports several different capabilities. This keeps the infrastructure relatively simple, but it also means those capabilities share a dependency and must be considered together when planning failure handling and reliability.
Overall, the main idea is to separate the user interface, request handling, business logic, data persistence, and background processing while keeping their interactions explicit.
